# CLAUDE.md — flutter-web-otpless (constitution)

Binding constitution for `flutter-web-otpless`, the source of the pub.dev package
`otpless_flutter_web`. It is not advice. If a change conflicts with an article
below, the change is wrong until an owner amends the article.

Cross-repo rules (parity, release trains, the contract spine) live in the hub
repo, `otpless-tech/native-sdks`. This file carries everything local.

---

## 0. Read this first — three facts that change how you should treat this repo

### 0.1 Nobody has published this package in over two years

`pubspec.yaml` says `1.2.6`. pub.dev's `1.2.6` was published **2024-05-21**, and
it is still `latest`. The last commit on `main` before this one was also
2024-05-21 (`version update 1.2.6`). 58 versions have been published in total,
none since.

Merchants are depending on a package nobody has shipped in over two years. That
is a statement of fact, not a criticism: it means (a) any bug fixed on `main`
after 2024-05-21 has never reached a merchant — there are none, `main` and
`1.2.6` are the same tree — and (b) the release path is unexercised, so the
first person to publish again should expect friction (pub.dev credentials,
`dart pub publish --dry-run` warnings, the SDK-constraint issues in §Article V).

Do not "fix" this by publishing. Publishing is an owner decision.

### 0.2 This package contains no authentication logic

It is ~110 lines of `dart:js` glue. Every flow is executed by a browser bundle
the merchant loads themselves, by hand, in `web/index.html`:

```html
<script data-appid="{APP_ID}" src="https://otpless.com/v2/flutter.js"
        id="otpless-sdk" type="text/javascript" variant="HEADLESS"></script>
```

`lib/src/otpless_web.dart` calls global functions that script installs
(`initiateAuth`, `verifyAuth`, `startHeadless`, `openLoginPage`) and installs one
of its own for the reply (`getResponse`). That is the whole design.

Consequences: this repo cannot fix an auth bug, and it cannot detect a
misconfigured merchant page (see §0.3 and the Known defects section). The bundle
is built in the **`vegapunk`** repo — `src/auth-files/flutter.ts` is the file
that implements the four globals above.

### 0.3 The JS-interop names are a contract no compiler checks

`js.context.callMethod('initiateAuth', ...)` is a **string** lookup on `window`.
Rename `initiateAuth` in `vegapunk`, or here, and:

- nothing fails to compile, in either repo;
- `flutter analyze` is silent;
- at runtime the call throws `NoSuchMethodError` into a Zone nobody is
  listening to, so the merchant sees *nothing happen at all*.

This is the same hazard class as a reflection contract. It is therefore treated
the same way: the names are committed as a golden at
**`api/js-interop-surface.txt`** and `make gate` diffs them.

**Source-file map** (there is no `docs/SDK-GUIDE.md`; at 110 lines the source is
the guide):

| File | Responsibility |
|---|---|
| `lib/otpless_flutter_web.dart` | The public library — one `export`. Nothing is public unless it is reachable from here. |
| `lib/src/otpless_web.dart` | Everything: `Otpless`, `OtplessResultCallback`, the six public methods, `getCodeForParams`, and `executeFunction` (the JS bridge). |
| `test/otpless_flutter_web_test.dart` | Chrome-only unit tests, including characterisation tests for the known defects below. |
| `tool/api_dump.dart` | Generates both surface goldens. |
| `scripts/check-analyzer-baseline.sh` | Analyzer info-drift check. |
| `example/` | A demo app. **Not** a test; not in the gate. |

## Article I — the public API is a contract, and pub.dev makes it permanent

Delivery channel: **pub.dev, package `otpless_flutter_web`**. Merchants write
`otpless_flutter_web: ^1.2.6` in their own `pubspec.yaml`. A bad release does not
go away when we redeploy something — it sits in merchant `pubspec.lock` files
until each merchant chooses to upgrade. (Contrast `vegapunk`, which is
CDN-delivered and has no version a merchant pins.)

- Public means: `Otpless`, `OtplessResultCallback`, and every public member and
  **parameter name** on them. Dart callers can and do use named-argument-style
  reading of these signatures in IDE tooltips; `request` → `payload` is a
  documentation break even where it is not a compile break.
- The surface is committed at **`api/public-surface.txt`**, generated by
  `tool/api_dump.dart`. Never hand-edit it. `make surface-update` regenerates it,
  and the change must be described in `CHANGELOG.md`.
- The **JS-interop surface** at `api/js-interop-surface.txt` is a second,
  cross-repo contract. Changing it is not a local change: the matching change
  must already have shipped in the CDN bundle built from `vegapunk`.
- The `channel` values this package injects (`"OAUTH"`, `"PHONE"`, `"EMAIL"`) are
  wire values, not local enums. They are pinned by tests.
- Version is single-sourced in `pubspec.yaml`. Do not restate it anywhere else —
  note that the README currently *does*, in its `flutter pub add` snippet; that
  line has to be updated by hand on every release, which is exactly the kind of
  drift the rule exists to prevent.

## Article II — never harm the host page

This runs inside a merchant's Flutter web app, on their document, sharing
`window`.

- **`window` is shared.** This package writes exactly one global,
  `getResponse`, and that is already one too many — see Known defects. Do not
  add another. If you need more state, keep it in Dart.
- **Never throw into merchant code.** Today failures do not reach the merchant
  at all, which is the opposite failure (Known defects #1). The fix is to
  *report* errors through the result callback, never to let an exception escape
  into their widget tree.
- **`kIsWeb` guard stays.** `executeFunction` returns early when `!kIsWeb`. This
  package is web-only; on any other platform every method must be a silent
  no-op, not a crash.
- Touch no DOM the merchant owns. `getCodeForParams()` only *reads*
  `window.location`.

## Article III — privacy and auditability

- **Never log a phone number, email, OTP, or token.** There is no logging in
  this package today and no logging framework. Keep it that way: `print` in a
  web build goes to the browser console, where anyone with the tab open reads
  it. (`example/lib/main.dart` does use `print`; the example is not shipped.)
- This package collects and transmits **nothing** of its own — no telemetry, no
  analytics, no HTTP. Everything it sends is the merchant's own request payload,
  `jsonEncode`d and handed to the browser bundle. A PR that adds a network call
  here is a data-collection change and must say so in its title.
- `getCodeForParams()` reads the `code` query parameter from the page URL. That
  is an auth artefact — do not log it, do not persist it, do not widen what is
  read from the URL without saying why.

## Article IV — naming

- Public symbol and parameter names are the contract (Article I); a rename is a
  breaking change, never a cleanup.
- Two existing inconsistencies are now permanent — do not "fix" them:
  - the library name in `lib/src/otpless_web.dart` is `otplessflutter_web`
    (missing an underscore) while the package is `otpless_flutter_web`;
  - `headlessResponse` is the Dart method name for the `startHeadless` global,
    and `verifyAuth` maps to a global of the same name. The mapping is not
    uniform.
- JS-global names must match the CDN bundle exactly, character for character.
  They are not ours to tidy.

## Article V — dependencies and weight

- **Runtime dependencies: `flutter` only. Keep it that way.** This package's
  value is that it adds nothing to a merchant's bundle.
- **Do not add a dev dependency that raises the SDK lower bound.** The published
  constraint is `sdk: ">=2.13.0 <4.0.0"`. pub resolves dev dependencies against
  that range too, so adding a package that needs Dart ≥3.4 forces the published
  constraint up and narrows who can install this package. That is why
  `tool/api_dump.dart` is written against `dart:io` alone instead of using the
  `analyzer` package.
  - Practical consequence to know about: because the declared language version
    is 2.13, newer Dart syntax is unavailable everywhere in this repo, tests
    included (for example an unnamed `library;` directive will not parse).
- No artifact-size budget and no shrinker review. There is no minification step
  in a pub package whose behaviour could surprise us, and the package is one
  source file. Reporting size here would be ceremony.

## Article VI — verification before merge

`make gate` is the **single definition of verified**. It is defined in exactly one
place, the `Makefile`; CI runs `make gate` and restates nothing.

    make install
    make gate

| Rung | Command | What it protects |
|---|---|---|
| format | `dart format --output=none --set-exit-if-changed .` | Formatting — also what keeps `tool/api_dump.dart`'s scanner reliable. |
| analyze | `scripts/check-analyzer-baseline.sh` | `flutter analyze --no-fatal-infos` (errors + warnings fatal) **plus** a diff of the info list against `analysis/analyzer-baseline.txt`. |
| test | `flutter test --platform chrome` | 11 unit tests. |
| surface | `dart run tool/api_dump.dart` | Both goldens: the public Dart surface and the JS-interop names. |

**Chrome is mandatory.** This package imports `dart:html` and `dart:js`, so the
Dart VM cannot compile it. A bare `flutter test` fails to *load* with
`Undefined name 'context'` — that is the VM refusing web-only libraries, not a
broken test. Always `--platform chrome`.

**Why an analyzer baseline instead of `--fatal-infos`.** The 8 current infos
include `dart:html`/`dart:js` deprecations that are real and must stay visible —
this package needs a `package:web` + `dart:js_interop` rewrite, and suppressing
the warnings with `// ignore:` would hide the biggest piece of technical risk in
the repo. So nothing is suppressed: the list is committed, and the gate fails if
it grows. Fixing one also fails the gate; accept it with `make analyze-update`.

**What green does NOT mean.** Every test stubs the browser bundle. Nothing in
this repo loads `https://otpless.com/v2/flutter.js` or reaches the OTPLESS
backend, and there is no widget or integration test at all. Green means the
JS-interop marshalling did not regress. It is not a coverage claim and it is not
evidence that authentication works. Any change to `executeFunction` or to the
JS-global names requires manual verification in a real browser against a real
app id — run `example/` with `flutter run -d chrome`.

`make example-build` exists but is **not** in the gate: it takes minutes and only
proves the example compiles, which no merchant depends on.

## Known defects — shipped, characterised, not fixed here

Each of these is pinned by a characterisation test in
`test/otpless_flutter_web_test.dart` under "known defects". Those tests assert
**wrong behaviour on purpose**. If one fails you have probably fixed the bug:
update the test and this section together. Never make one pass by reverting.

1. **Failures are swallowed.** `executeFunction` is declared `async` but returns
   `void`. When `js.context.callMethod` throws — which is exactly what happens
   when the merchant's `index.html` is missing the script tag or the
   `variant="HEADLESS"` attribute — the error goes to the enclosing Zone. A
   merchant app installs no Zone handler, so it goes nowhere. Worse: the
   `getResponse` callback is registered *after* the failing call, so it never
   gets registered either. The merchant's symptom is "the button does nothing",
   with no exception and no callback, ever. **This is the highest-value fix
   available in this repo.**

2. **`getResponse` is a single global slot.** Every call overwrites the previous
   callback. Two concurrent requests cannot coexist: a late reply to the first is
   delivered to the second caller's callback. Fixing it properly means
   correlating requests, which is a contract change (needs a request id) and so
   is a cross-repo change with `vegapunk`.

3. **`verifyAuth` drops every response that is not `ONETAP`.** See
   `executeFunction`: for `verifyAuth` the callback fires only when
   `responseType == "ONETAP"`. A `FAILED` response to a wrong OTP therefore never
   reaches the merchant through `verifyAuth`. Merchants must additionally call
   `headlessResponse` to see failures — which the README does not say.

4. **`Otpless()`'s constructor has a side effect.** If the page URL carries a
   `code` query parameter, constructing `Otpless()` calls `headlessResponse`
   with a do-nothing callback. So `Otpless()` is not a pure constructor and
   constructing it twice is not free.

## The web contract DIVERGES from native — do not copy a native guide's contract section

The hub's `docs/PARITY.md` §E is the ledger. It was written against
`otpless-headless-js`, and the divergences it records apply to the whole web
family because they originate in the shared browser bundle:

- The web envelope carries **`success: boolean`**, which no native SDK sends,
  and `response` is optional. This package never constructs that envelope — it
  passes a JSON **string** straight through — but the *bundle* does:
  `vegapunk/src/auth-files/flutter.ts` builds
  `{responseType: "ONETAP", response, statusCode: 200, success: true}`.
- Web event vocabulary diverges both ways: `SESSION_END` and `LOADING_STATE`
  exist on web only; seven native response types (`INITIATE`, `VERIFY`,
  `SDK_READY`, `DELIVERY_STATUS`, `AUTH_TERMINATED`, `MFA_FACTOR_COMPLETED`,
  `AUTO_FLOW_ACTION`) do not appear on web.
- Web channels are the coarse `PHONE` / `EMAIL` / `OAUTH` buckets — this package
  injects exactly those three strings — against native's much larger channel
  enum.

**Never import a native SDK's response-contract documentation into this repo.**
This package is not even typed against the response: `OtplessResultCallback`
takes `dynamic`, and what arrives is an unparsed JSON `String`. A contract
change in the bundle changes this package's behaviour with zero code change
here, which is precisely why PARITY.md exists.

## Sibling repos you will need

| Repo | Relationship |
|---|---|
| `vegapunk` (`frontend/web/vegapunk`) | Builds the CDN bundle this package calls. `src/auth-files/flutter.ts` implements `initiateAuth`, `verifyAuth`, `startHeadless`, `openLoginPage` and calls `getResponse`. **Caveat:** its webpack config builds the `v5` path, while this package's README tells merchants to load `v2/flutter.js` — so `vegapunk` `main` is not provably the source of the bundle in production. Two sibling repos (`websdk`, `sdk-v2`) declare the same unpublished package name; which is canonical is **unresolved**. |
| `otpless-headless-js` | The other web client (npm). Wraps `v4.3/headless.js` from the same family of bundles. |
| `flutter-headless-sdk` | The **mobile** Flutter plugin (`otpless_headless_flutter`), pinning the native Android/iOS SDKs. Different package, different contract — do not confuse the two. |

## Working rules

- **Worktree-driven development.** The primary checkout belongs to the human.
  Every independent task gets its own worktree:

      git worktree add -b <branch> /tmp/flutterweb-<task> origin/main
      # work, commit, push from there
      git worktree remove /tmp/flutterweb-<task>

- **Never push `main`.** Every change goes through a PR.
- **Never hand-edit `api/*.txt` or `analysis/analyzer-baseline.txt`.** Generated.
- **`make gate` before every PR**, with the real output pasted into it.
- **Do not add a test that cannot fail.** Break what it guards once, confirm the
  failure, revert.
- **Do not commit `example/build/`.** It was committed historically; this branch
  removes it and `.gitignore` now covers it.

## What this repo does NOT have (be honest about it)

- No `docs/SDK-GUIDE.md` — by decision; §0 carries the map.
- No widget test, no integration test, no e2e test. The browser bundle is never
  really loaded.
- No coverage threshold. 11 tests is not a coverage claim.
- No release automation, and a release path that has not been used since
  2024-05-21.
- Platform documentation does not live here. It lives in the private
  `otpless-tech/atlas` repo, wired up by `.github/workflows/atlas-docs.yml`.
